# Task Template

## Title

Use an outcome-oriented title.

## Context and user value

Explain the problem, affected user, and why the work matters.

## Desired outcome

State the observable result, not merely implementation activity.

## In scope

- Explicit behavior and components included.

## Out of scope

- Adjacent behavior that must not be added.

## Governing documents

- Link product, architecture, security, UX, SDK, and ADR sections.

## Proposed ownership

- Expected project(s)/layer(s).
- New public contracts, if any.
- Persistence/migration impact, if any.

## Acceptance criteria

Use verifiable statements:

- [ ] Given ..., when ..., then ...
- [ ] Error/cancellation/unsupported states ...
- [ ] Security invariant ...
- [ ] Cross-platform/provider behavior ...
- [ ] Documentation ...

## Required tests

- Unit:
- Integration:
- Architecture:
- UI/manual:
- Security/negative:

## Security and privacy notes

Describe credentials, privilege, host identity, command input, output sensitivity, audit, and retention effects. Write `None` only after checking.

## Compatibility and migration

Describe plugin API, schema, settings, OS/provider, and downgrade implications.

## Completion evidence

- Build/test commands.
- Screenshots or logs, redacted.
- Demonstration scenario.

## Follow-ups

List genuine deferred work as separate issues. Do not use follow-ups to hide incomplete acceptance criteria.
